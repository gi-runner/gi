# Karate-to-Go audit — 18 October 2026

**Verdict: gi is a promising, compact Karate-inspired runner, but it is neither close to full Karate parity nor ready for a Staff-level production-quality sign-off.** The blockers include observable correctness defects, not merely style preferences or missing convenience functions. The no-JVM goal is achieved for the CLI build; browser testing still requires an installed Chrome.

This evaluates the code, not the seniority of its author. “Staff quality” is a judgment about dependable behavior, coherent contracts, maintainability, and the evidence supporting them. It is not a certification or an aesthetic score.

| P1 | **HTTP latency excludes reading the body.** A response whose headers arrive immediately and body arrives 120 ms later records about 1.1 ms. | P1 | **Cancellation can return success.** A nominal one-hour load run cancelled after its first successful response returns `Passed=true` after roughly 54 µs. **Additional source-confirmed issues and risks.** These were identified by inspection, not separate targeted reproductions in this audit.

- Load workers discard `engine.RunFile` errors by returning silently. The caller loses the failure reason, and no shared error is propagated. A run with earlier successful requests can therefore have an incomplete execution history without a corresponding error result. The load duration is checked only between iterations: long requests, calls, or scripts can run past the window. [load.go:137](/Users/arun/development/workspace/github.com/gi-runner/gi/internal/load/load.go:137).
- The rate limiter goroutine lives until the *caller’s* context ends, rather than until `load.Run` returns. Repeated runs with a long-lived context retain tickers/goroutines. Samples are retained twice per request (overall and endpoint), copied during merge, and copied again for sorting: memory grows with total requests rather than staying bounded. [load.go:193](/Users/arun/development/workspace/github.com/gi-runner/gi/internal/load/load.go:193), [load.go:448](/Users/arun/development/workspace/github.com/gi-runner/gi/internal/load/load.go:448).
- Kafka `Receive` consumes a whole fetched batch but returns only its first record; the remaining fetched records are dropped from the adapter's observable stream. [kafkax.go:48](/Users/arun/development/workspace/github.com/gi-runner/gi/internal/kafkax/kafkax.go:48). Retain pending records or poll only one record.
- Channel operations use the scenario parent context with no configured operation timeout. Browser methods accept a context but ignore that argument in favor of the stored page context. Suite cache waits receive on `f.wait` without context support; recursive/cyclic cache dependencies can hang. [channel.go:23](/Users/arun/development/workspace/github.com/gi-runner/gi/internal/engine/channel.go:23), [browser.go:29](/Users/arun/development/workspace/github.com/gi-runner/gi/internal/browser/browser.go:29), [suite.go:108](/Users/arun/development/workspace/github.com/gi-runner/gi/internal/suite/suite.go:108).
- Only the last file’s load result is retained in HTML/JSON. Load JUnit is built from empty `FileResult.Scenarios`, so threshold failures are not represented as failing test cases. [cli.go:239](/Users/arun/development/workspace/github.com/gi-runner/gi/internal/cli/cli.go:239), [report.go:44](/Users/arun/development/workspace/github.com/gi-runner/gi/internal/report/report.go:44). Console/exit status and report evidence can disagree.
- Request headers/bodies are captured without a masking policy. Authorization values can enter HTML/JSON artifacts. OTLP timestamps use the document start for every scenario/request instead of their actual starts, and child calls are not traversed. [engine.go:941](/Users/arun/development/workspace/github.com/gi-runner/gi/internal/engine/engine.go:941), [otel.go:48](/Users/arun/development/workspace/github.com/gi-runner/gi/internal/report/otel.go:48).
- OAuth client-credentials tokens are cached without expiry/refresh handling. Custom pooled transports start from a zero-value `http.Transport`, losing useful default proxy/dial/TLS configuration unless deliberately supplied. [auth.go:72](/Users/arun/development/workspace/github.com/gi-runner/gi/internal/engine/auth.go:72), [client.go:23](/Users/arun/development/workspace/github.com/gi-runner/gi/internal/httpx/client.go:23).
- XML conversion discards namespace identities, mixed-content ordering, and cross-name sibling ordering; formatting sorts child names. This cannot preserve general XML semantics. [xml.go:52](/Users/arun/development/workspace/github.com/gi-runner/gi/internal/xml/xml.go:52), [xml.go:121](/Users/arun/development/workspace/github.com/gi-runner/gi/internal/xml/xml.go:121).

**Engineering-quality assessment.**

There is real good work here: a small dependency-injected `Sender`, separate scheduling and execution packages, ordinary structs and explicit errors, sensible use of the standard library, deterministic report ordering, isolated scenario VMs, a distinct missing-value representation, and integration tests with local services. Formatting and vet are clean. This is a workable foundation, and replacing it wholesale would be premature.

| Criterion | Judgment | Why |
|---|---|---|
| Idiomatic Go | Mixed, with a sound foundation | Value types, small interfaces, context parameters and explicit error returns are good. Contexts are not consistently honored; error information is sometimes swallowed; resource ownership is incomplete. |
| Clarity/KISS | Mixed | Most functions are readable. But the dual variable store and retry-on-any-error evaluator hide surprising behavior behind short code. Simplicity must include semantics, not just line count. |
| DRY | Partial | Test and load share the main executor. Called features reimplement execution and lose capabilities; CLI and engine duplicate scheduling logic; string-scanning helpers repeat with differing grammar support. |
| SOLID in Go terms | Partial | `Sender` is a good consumer-defined seam. `Link` forces gRPC to implement unsupported Send/Receive and WebSocket/Kafka to implement unsupported Call, illustrating a poor interface fit. Prefer capability interfaces or distinct protocol types, rather than an all-purpose abstraction. |
| Concurrency/lifecycle | Below sign-off bar | Race checks pass, but they cannot prove cancellation, no leaks, deadlock freedom or correct result reporting. Limiter lifetime, uninterruptible JS, cache waits and child option propagation need explicit contracts. |
| Performance | Unproven and currently risky | No benchmarks; repeated normalization/copying, parsing called files repeatedly, retaining every latency sample, and backtracking/greedy matcher behavior need measurement and redesign where justified. |
| Test discipline | Useful beginnings, insufficient semantic coverage | Happy-path integrations pass while 17 focused edge/compatibility probes fail. A DSL and assertion engine need conformance fixtures, adversarial cases and fuzzing at parser/representation boundaries. |
| Public/operational contracts | Early stage | No public embedding API, incomplete compatibility policy, incomplete artifact masking/cancellation/report semantics. Go dependency declarations also mark many directly imported dependencies indirect; module hygiene needs a tidy review. |

Rob Pike's [Go Proverbs](https://go-proverbs.github.io/) and Dave Cheney's [SOLID Go Design](https://dave.cheney.net/2016/08/20/solid-go-design) favor clarity, useful small interfaces and understandable composition. The code reflects some of these ideas, but does not consistently deliver their outcomes. The official [pipeline cancellation guidance](https://go.dev/blog/pipelines) also makes shutdown part of the design. That article is by Sameer Ajmani; it should not be attributed to Pike. More goroutines, design patterns or interfaces would not by themselves improve this implementation. Neither author offers a “Staff-quality” certification, and I cannot claim either would endorse this code.

**Recommended order of work.**

1. **Restore trust in existing behavior.** Fix false-positive matching, double JS execution, variable coherence, numeric fidelity, URL escaping, body handling, cookie state, complete HTTP timing and cancellation. Convert the isolated probes into regression tests as each contract is adopted.
2. **Unify execution semantics.** One internal execution path for top-level/called/setup scenarios with explicit policies for inherited configuration, variable scope, hooks, telemetry, resource ownership and cancellation. Keep a plain step dispatcher if it remains clearest; avoid an elaborate plugin framework merely to remove a switch.
3. **Publish a versioned compatibility contract.** Pin a Karate commit/version, separate exact syntax compatibility from native replacements, list intentional exclusions, and use upstream feature fixtures for an automated differential suite. Start with HTTP/JSON/calls/config/mock semantics before expanding browser/protocol breadth. Do not publish a parity percentage without a defined, weighted denominator and executable checks.
4. **Make load and reporting dependable.** Context-owned limiter lifecycle, bounded latency histograms/sketches, explicit window/overrun semantics, surfaced worker failures, complete call metrics, per-file load results, meaningful JUnit threshold failures and redaction.
5. **Harden the boundaries.** Fuzz path parsing, embedded expressions, match parsing, malformed XML and numeric boundaries; test deadline/leak behavior and repeated receives; benchmark representative workloads. Add race/vet/build/conformance checks to CI and document supported Go/platform/browser versions.

I would presently describe this as an **early native testing runner with a substantial core**, suitable for controlled use of its verified subset. I would not market it as a drop-in or near-complete Karate port, or sign it off as a production-grade Staff-quality implementation, until the correctness and contract gaps above are addressed.
